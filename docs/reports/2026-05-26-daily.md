## 今日最大的事：AI 工具进入“反 slop / 算账 / 上下文资产化”阶段

### 1. “The Eternal Sloptember”：AI 反感从版权/就业扩展到软件质量与安全文化

- HN: [The Eternal Sloptember](https://geohot.github.io//blog/jekyll/update/2026/05/24/the-eternal-sloptember.html) — 460 points / 357 comments。
- 讨论点不是简单“AI 写代码好不好”，而是 AI 生成内容会不会制造一个永不结束的 September：大量低质量输出进入代码、issue、文档、安全报告，增加人类 triage 成本。
- 评论区有两类声音：一类强调 AFL/模糊测试也不是“工具自己找到漏洞”，而是工具触发信号后由熟练人类或 agent triage；另一类认为 2026 年的 coding agent 能力已经跨过临界点，身边人开始真实使用，但物流/能源/GPU 约束会限制继续指数增长。

【判断】这对 agent PM/eval 很关键：评估 agent 不能只看它产出多少，而要看它给系统增加还是减少“待 triage 噪音”。一个好指标是：每次 agent 输出之后，人类需要检查多少条、撤回多少次、修正多少隐藏约束。Margin/个人 AI 同事也一样，最危险的不是答错，而是把用户的信息空间变脏。

### 2. Uber tokenmaxxing：AI 预算开始被运营层严肃审视

- HN: [Uber’s COO says it’s getting harder to justify money spent on tokenmaxxing](https://www.businessinsider.com/uber-coo-andrew-macdonald-ai-token-spending-harder-justify-2026-5) — 219 points / 288 comments。
- “tokenmaxxing”这个词本身值得记：企业内部对 AI 的态度正在从“多试试”转向“为什么要花这些 token”。
- 这和昨天的 memory cost / DeepSeek cache / codegraph 信号连成一条线：AI 成本不是抽象云账单，而是影响产品形态的约束。长上下文、反复 agent loop、无缓存工具调用都会被运营层拿出来问 ROI。

【判断】AI 产品 activation 的下一阶段，不是展示“我能生成更多”，而是展示“我替你省掉了哪些重复上下文重建、搜索、沟通、检查”。如果无法量化减少了多少人工/时间/错误，用户很快会把它归为 tokenmaxxing。

### 3. “Using AI to write better code more slowly”：高质量 AI 编程可能是慢下来，而不是自动化到底

- HN: [Using AI to write better code more slowly](https://nolanlawson.com/2026/05/25/using-ai-to-write-better-code-more-slowly/) — 509 points / 196 comments。
- 这篇的价值在标题：AI 不必只服务于“更快写更多代码”，也可以服务于“更慢地验证、更清楚地理解、更谨慎地改”。
- 和 Constraint Decay 论文、Sloptember 讨论放在一起看，coding agent 产品的差异可能从“帮你写”转向“帮你想清楚再写”：拆约束、解释 tradeoff、写测试、生成小 diff、保留审查上下文。

【判断】这对一人公司尤其重要：独立 builder 最缺的不是敲代码速度，而是没有同事帮你做反方审查。AI coding 的高阶价值是成为 reviewer / pair programmer / constraint keeper，而不是一味扩大输出面积。

### 2. California Linux age-verification backlash：平台政策会继续挤压开源和本地计算边界

- HN: [California moves to exempt Linux from its age-verification law after backlash](https://www.tomshardware.com/software/linux/california-moves-to-exempt-linux-from-its-upcoming-age-verification-law-after-backlash-over-forcing-operating-systems-to-collect-users-ages-amendment-proposed-by-the-same-lawmaker-who-wrote-the-original-law) — 820 points / 351 comments。

【判断】这不是 AI 新闻，但和 local-first / browser agent 有关：任何依赖平台权限、身份、内容访问的产品，未来都会被政策边界影响。个人 AI OS 如果要接浏览器、iMessage、文件系统，必须设计成用户可见、可撤销、最小权限，而不是黑盒常驻。

## 赛道雷达

### MCP / Memory / Context Layer

Unabyss 的票数和 GitHub Trending 的 knowledge graph 一起说明，MCP 的下一步不是“连接更多工具”，而是“连接工具之后，如何让上下文持续更新并被正确复用”。这和用户正在搭的 iMessage command channel 也有关：入口只是第一步，真正价值在长期上下文和状态。

### Agent PM / Eval

今天的 eval 关键词是 slop rate、constraint retention、triage cost、token ROI。一个 agent PM 面试可以这样回答：先定义任务约束与失败成本，再看 agent 是否减少人类检查负担，而不是只看 benchmark 分数。

### AI 产品留存

搜索替代、tokenmaxxing、slop 反感都说明：AI 产品留存来自可信、克制、可解释的工作流。用户愿意为 Unabyss / Yansu 这类产品投票，是因为它们承诺“懂我的长期上下文”；但如果输出变脏或成本不可控，留存会很快崩。

## Builder Takeaways

1. **给 iMessage/Hermes bridge 加 conversation mode**：天气这种多轮问答如果每句都要 `@h`，体验会断；但无前缀处理必须有短时上下文窗口和防误触发。
2. **为 agent 输出记录 slop/triage 指标**：不仅记录“完成了吗”，还记录“用户需要修多少”。
3. **把上下文做成资产，而不是每次重新收集**：Unabyss/codegraph/tweet.md 都说明结构化、可复用上下文是下一个竞争点。
4. **避免 tokenmaxxing 式自动化**：自动跑很多 agent 不等于有效，应该有成本、失败、价值的最小仪表盘。
5. **技能库是产品化入口**：从 cybersecurity skills 到 knowledge-work plugins，垂直 skills 可能比通用 agent 更容易让用户信任。
